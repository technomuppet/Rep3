# RC20.3A — Performance Report

## Frame Rate (Theoretical)

- **Baseline RC20.2:** 60 draw ops per frame (10 capsules 40 ops, torso 4 paths, equipment 7, floor 3, hands 2) ~60fps high-end.
- **RC20.3 additions:**
  - Base FK 38 objects (mutableMap 19 + 19 SolvedJoint)
  - TopBar/bottomBar extra 2 FK solves per frame = 76 objects (2*38) — **regression**, should be cached via remember per timeline.
  - HybridSolver: bone lengths 8 hypot, 4*FABRIK 3 joints 10 iter each 40 hypot per limb => 160 hypot + 2*mutableList, map copy 19 entries => ~60 objects.
  - COM 15 segments loop cheap 1 object ComResult.
  - Stabilisation 6 checks cheap.
  - BarPath sin lerp cheap.
  - Body renderer 2 Path allocations torso + equipment 1 line 6 rects.
  - Total per frame ~38+76+60+2 = 176 objects vs 38 before. At 60fps = 10,560 objects/sec GC pressure may cause jank mid-range.
- **Measured expectation:** High-end Pixel 7 60fps possible, mid-range Pixel 4a 45-55fps without cache, with cache top/bottom (remove 76) => 100 objects/frame => 60fps mid-range possible.
- **Caching Opportunities:** Cache topBar/bottomBar once per timeline in remember (saves 76), pre-bake timeline evaluations into FloatArray lookup 60fps*duration (156 poses) to avoid FK+interpolator allocation (saves 38+ map), object pooling for SolvedSkeleton joints map, Path pooling for torso.

## Memory Allocations

- **Unnecessary allocations identified:**
  - `ForwardKinematicsSolver.solve` mutableMap + 19 SolvedJoint per solve (3 times per frame due to top/bottom + base).
  - `PoseInterpolator.interpolate` mutableMap + SkeletalPose per evaluation.
  - `IKSolver.solveFABRIK` mutableList 3 Offsets per limb per frame.
  - `HybridSolver` map copy.
  - `SkeletalRenderer.drawCommercial` referenceSize Float cheap, but `LayeredRenderingPipeline.RenderContext` data class allocation per frame.
  - `HumanBodyRenderer` 2 Path objects chestPath abdomenPath per frame.
  - `EquipmentRenderers` Plate colors list static immutable good, but Path for EZ bar and rope loops per frame.
  - `ExerciseAnimationView` CommercialAnimationCanvas still triggers Column recomposition each frame via mutableFloatStateOf elapsedSeconds — Row controls also recompose.

- **Zero allocation claims:** Old comments claimed zero allocation inside draw loops but were false (FK allocated map). New code still allocates but less than before for main path? Actually more due to hybrid. Claim of zero unnecessary allocations in RC20.2 docs was overstated. RC20.3 adds more.

- **Cached geometry:** Anthropometry constants singleton good, BoneCatalog ALL_BONES list static good, EquipmentEngine allRenderers list static good, MuscleRenderer paths prebuilt once good (FrontBody/BackBody built via buildPath object init zero alloc during draw). VolumetricRenderer no Path for limbs (drawLine + drawCircle only) good.

- **Minimal recomposition:** Not achieved — elapsedSeconds State triggers Column recomposition. Should isolate Canvas composable with its own State. Performance report RC20.2 noted this, RC20.3 still not fixed.

## Recomposition Frequency

- **Current:** Every FrameNanos (~16ms) elapsedSeconds updates -> triggers recomposition of Column containing Canvas + Row controls. Row with IconButtons also recomposes each frame but cheap.
- **Canvas redraw frequency:** Every frame (via State change) — expected, need redraw.
- **Should be:** Only Canvas recomposes, not Row. Use `Canvas(Modifier.drawWithCache { ... })` or separate composable `CommercialBodyCanvas` that takes elapsed as param and uses `remember {}` inside.

## Solver Performance

- **FK solver:** 19 joints * cos/sin per joint = 19 trig ops per solve, 3 solves per frame = 57 trig ops, cheap.
- **FABRIK:** 3 joints *10 iter * (hypot + division) per limb = 30 hypot per limb *4 limbs = 120 hypot, cheap <0.3ms.
- **Timeline evaluation:** Linear scan O(n) n=3-4 keyframes cheap.
- **BarPathEngine:** sin lerp cheap.
- **COM:** 15 segments lerp cheap.

## Equipment Rendering

- **Cost:** Each equipment renderer draws 1 line + 2-6 rects/circles, cheap. OlympicBarbell draws 1 line + 6 rects + 2 circles = 9 ops.

## Muscle Rendering

- **Cost:** MuscleRenderer drawBody with withTransform scale, 2 paths silhouette + primary/secondary regions up to 27 paths but only primary/secondary sets drawn (typically 2-4 paths). So 3-5 drawPath per front+back = 6-10 paths. Acceptable.

## Bottlenecks

1. **TopBar/bottomBar per frame 2 FK solves** — biggest regression, easy fix cache.
2. **FK + interpolator allocations** — pre-bake lookup tables.
3. **Column recomposition** — isolate Canvas.
4. **Path allocations torso 2 per frame** — pool.

## Caching Opportunities

- Cache topBar/bottomBar via `remember(timeline) { compute once }`.
- Pre-bake timeline evaluations: `val baked = remember(timeline) { (0..(duration*60).toInt()).map { t -> timeline.evaluate(t/60f) } }` then per frame lookup index = (elapsed*60).toInt() % size.
- Object pool for SolvedSkeleton joints map via `MutableMap` reuse.
- Path pool for torso.

## Scaling, Rotation, Screen Sizes

- **Scaling:** referenceSize = min(width,height)*0.32 ensures body scales cleanly across display sizes, thickness multiplied by referenceSize, shoulder width via hypot actual solved positions coerceAtLeast 0.18*ref.
- **Rotation:** BodyOrientationEngine rotates upper vs lower around pelvis cos/sin, supports standing, seated, supine -90, prone 90, incline +30, decline -15, hanging -0.15 shift. Early return no alloc for standing.
- **Screen sizes:** Canvas fillMaxWidth height 240dp, toScreen width*x height*y responsive.

## Dark/Light Mode

- BodyPalette.fromMaterial(primary, onSurface) skin neutral #D8BFA0 warm, shirt = primary (MaterialTheme), shorts #2E2E3A, shoe #1A1A1A, outline onSurface alpha 0.35, hair #2B2B2B. Adapts via primary/onSurface from MaterialTheme, skin stays neutral acceptable. Muscle palette dark/light bodyFill slate 800/200 primaryFill red 500 etc.

## Landscape/Portrait/Tablet/Phone

- Code uses width/height scaling, referenceSize min, so landscape wider still scales, portrait taller scales. Tablet larger width height still scales. No specific landscape layout (Canvas height fixed 240dp may be small on tablet, but fillMaxWidth helps).

## Summary

- Frame rate theoretical 60fps high-end, 45-55 mid-range without cache, with cache 60 mid-range.
- Allocations increased from 38 to 176 objects/frame due to top/bottom extra FK and hybrid, should be optimized.
- Recomposition frequency too high (Column).
- Solver performance cheap.
- Caching opportunities identified and easy to fix.
- Not yet fully 60fps solid on all devices, but acceptable for commercial release on high-end.
